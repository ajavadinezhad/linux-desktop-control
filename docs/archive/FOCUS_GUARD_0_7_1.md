# Consent-first foreground guard — 0.7.1

> Version-specific investigation record. Status statements below describe that checkpoint. See [current release status](../RELEASE_STATUS.md) for installed versions and later acceptance.

The preceding Firefox test confirmed a real gap: the user deliberately used Alt+Tab, and an unfenced sequence continued. The earlier app launch was performed by a command runner before consent; this bypassed the intended orchestration boundary, not the portal's consent enforcement. Both behaviors are now prohibited/guarded. No new live test has run for this version.

The observer reads GNOME51's focus-window, a stable window sequence number, frame rectangle and Shell context. It subscribes to focus, window position/size, lifecycle/workspace/monitor-scale and overview/session-mode changes. A monotonic epoch invalidates switching away and back. It reads no window titles, app content or key/mouse events and never grabs focus or modifies the cursor. Geometry and context are also polled at event fences, so lock/overview/foreign modal changes cannot be handled merely by hiding the label.

An inspected image binds an opaque single-use window_observation_id to identity, geometry, context epoch, session generation and a 60-second lifetime. Ordinary pointer/keyboard/scroll/drag batches check it before each event, at interruptible wait boundaries, after the final event and before/after screenshot capture. Foreground losses cancel remaining input, raw-release held state, close the portal and invalidate queued generations. Focus reclamation/automatic retry/restart is absent. Optional accessibility identities also refuse changed field focus; GrabFocus is no longer available in that transport.

The exception is an explicit focus_transition=true action containing only one left click or launcher/Return gesture. It enables normal GUI app launching without a batch of unchecked typing after a switch. The returned image must be inspected before anything else. It authorizes a deliberate transition only and cannot identify a simultaneous human switch. Unexpected observed results require closure and explicit user readiness, never automated reacquisition.

Consent-first orchestration: no shell, subprocess, xdg-open, wmctrl, D-Bus app launch/focus or manual fixture before successful personal sharing and actual fresh-image inspection. examples/consent_first.py has no app command runner and permits only observed GUI launching. Denied/cancelled/missing/uninspected images cannot launch anything. Fixtures in demo/app.py and tests/target_fixture.py are for manual isolated use, not live preconsent orchestration.

The regression matrix includes focus changes during movement, typing, dragging and scrolling; away/back epochs; x/y/width/height changes; closed/unmanaged windows; lock, overview and foreign system modals; revoked portal input and revocation during capture reconnect; post-input/pre-image races; key/button release; stale queued work; no automatic replay/refocus; and denied consent ordering. Tests use fake transports/actors and event injection, not the live user's input devices. Existing core tests remain.

Limits: signals/polling and OS input dispatch are not atomic. An event already accepted by GNOME may take effect before cancellation. Identical foreground/context/geometry does not establish human inactivity or exclusive ownership; same-window mouse movement/field changes can escape this guard. Optional accessibility may catch field changes but can be unavailable. Intentional geometry changes and cross-window drags are conservatively restricted. No universal toolkit/desktop support, no guaranteed instantaneous cleanup, and no resolution of the old pointer-jitter symptom is claimed. Native GNOME sharing termination remains available independently.

Installed files alone do not replace in-memory GNOME extension code. The backend verifies protocol 2 before requesting consent and refuses older code. A manual logout/login may be required; no session restart is automated.
